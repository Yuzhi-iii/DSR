# 4. Requirement Mapping Logic

## 4.1 Mapping principle

Requirement mapping translates extracted case facts into requirement-level assessment statuses.  
Each requirement is evaluated in three stages:

1. trigger determination  
2. fact-to-requirement assessment  
3. assignment of a requirement status and local recommended action  

The mapping layer does not produce final legal conclusions.  
Instead, it determines whether a requirement is triggered, sufficiently evidenced for procurement-stage screening, insufficiently documented for reliable screening, or indicative of a potentially problematic condition requiring escalation.

This Markdown specification must be interpreted in strict conformity with the JSON requirement rules.  
Where the JSON uses narrower, context-sensitive, or combination-based logic, that JSON logic controls.

In the current JSON-aligned version, not all requirements make equivalent use of all four statuses.

In particular:

- `MR2`, `MR3`, `MR5`, and `MR8` do not define a distinct substantive `potential_gap` assessment rule in the current JSON implementation.
- `MR4` and `MR6` use explicitly context-sensitive screening logic.
- `MR1` uses a narrower `potential_gap` rule than a generic “sensitive processing plus unclear basis” formulation. Only the operationalized higher-risk combinations listed above produce `potential_gap`.
- `MR7` uses a narrower trigger and escalation model than a general transfer-relevance formulation. In the current JSON implementation, explicit cross-border transfer indication is the operationalized basis for `potential_gap`.

This reflects the screening-oriented design of the prototype, where some requirements are used to detect substantive escalation signals, while others are used to detect whether the case materials are sufficiently complete and intelligible for further assessment.

## 4.3 Status assignment logic

The requirement mapping layer uses four requirement-level statuses:

- `met`: the requirement is triggered and the available facts support a satisfactory screening-stage assessment
- `insufficient_information`: the requirement is triggered, but the available facts do not support a sufficiently reliable assessment
- `potential_gap`: the requirement is triggered and the available facts indicate a potentially problematic condition for compliance screening under the specific operationalized rule combinations defined in JSON
- `not_triggered`: the requirement is not applicable based on the extracted facts

These statuses are used as structured intermediate outputs.  
They support downstream escalation, risk classification, and explanation generation in the rule-based decision layer.
